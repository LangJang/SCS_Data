## 1. 目的与范围

**目标**：南中国海（SCS）多源海洋数据（物理海洋 + 生态 + 渔业）的采集、标准化、存储、检索与内部使用。

**规模**：当前约 180 GB，目标数百 TB。按 C7，数百 TB 来自现有类型数据在**时间维度**上的扩张（更多年份、更高时间分辨率），而非引入新变量或新观测系统。

**边界**（按 C2–C7 划定）：
- 不做数据完整性校验、不做质量控制、不做备份冗余；
- 不做网络分发、不做公开 DOI；
- 数据种类冻结，canonical 变量体系维持现状。

## 4. 数据处理与标注

### 4.1 处理流程（已实现，沿用）
```
原始 NetCDF → detect_source() → adapter.adapt() → SourceMeta（canonical）
   → 重采样/重网格（0.05°）→ 分层（14 层 0–400 m）
   → 懒加载访问（dask，按时间维分块）→ 可视化 / 导出（CSV/Excel/NetCDF）
```

### 4.2 标注（元数据）——与「质控」的区分

**关键区分**：按 C3「不做质量控制」，指的是不做**逐值质量标注**（QC flag 如 1=good/4=bad）；但「元数据目录」用于**发现与溯源**（某个文件是什么、覆盖哪里、何时、在哪块盘），不做它数百 TB 就无法检索。两者不是一回事。

| 标注层次 | 内容 | 现状 | 决策 |
|---------|------|------|------|
| 数据集级 | 名称、来源、变量、时间/空间覆盖、分辨率、垂直层 | ✅ 在 `config.yaml` | 保留并升级（§7 阶段 1） |
| 变量级 | canonical 名 + 单位 | ✅ 在 `canonical.py` | 冻结（C7） |
| 溯源 | 来源 + 处理步骤（标准化历史） | ⚠️ 部分，散在脚本 | 阶段 1 补齐 |
| 质量标注 | QC flag | — | **不做**（C3） |
| 完整性 | checksum | — | **不做**（C2） |

> 标注原则：只做「发现与溯源」，不做「质量与校验」。这与 C2/C3 一致，也把元数据的工作量降到最低。

## 5. 存储与分层（冷存储为主）

### 5.1 核心判断

数百 TB 的「数据库」**不是把数据塞进数据库管理系统（DBMS）**，而是：

```
数据本体 = NetCDF 文件，放在分层文件系统（冷为主）
   ↑ 索引
元数据目录 = 一个轻量目录（存「每个文件是什么、覆盖哪里、在哪块盘」）
   ↑ 驱动
计算层 = 现有 xarray + dask（按需读块，绝不整库入内存）
```

### 5.2 分层（按 C5 冷为主）

| 层 | 介质 | 内容 | 量级 |
|----|------|------|------|
| 热 | NVMe/SSD | 正在处理/分析的数据、标准化产物 | 几 TB |
| 冷 | 大容量 HDD | 原始 NetCDF（ROMS/CMEMS 全量） | 数百 TB，按需挂载 |

访问纪律：冷数据**按需挂载、懒加载读取**，全量常驻只有目录层。

### 5.3 单机 Windows 的现实约束

| 约束 | 数值 | 应对 |
|------|------|------|
| NTFS 单卷上限 | ~256 TB | 数百 TB 需**多卷/多盘**，按「来源 + 时间」分盘 |
| NTFS 单文件上限 | ~16 TB | 单个 NetCDF 保持在此之下；跨年大文件按时间拆开 |
| 无冗余（C4） | — | 见 §8 风险提示 |

**分盘策略**：冷数据按「来源 × 时间区间」落到不同盘，元数据目录记录每个文件的**盘符 + 相对路径**，检索时目录先定位盘、再懒加载。

### 5.4 原始层不可变 + 处理层可重建

即使不备份（C4），也应坚持一条纪律以降低损坏面：

- **原始层只读、不可变**：下载/接收的原始 NetCDF 落盘后不再覆盖。
- **处理层可重建**：标准化产物从原始层重算得到，产物丢失可重跑脚本再生（但自采渔业、自跑 ROMS 输出无源，属例外，见 §8）。

### 5.5 分块（chunking）

沿用现有做法——按时间维分块（`chunks={"ocean_time": 1}`），冷数据同样按时间分块。是否迁移到 Zarr（分块/并行/云原生的现代格式）**列为可选、不强制**；在「单机 + 冷为主 + 现有 NetCDF 链路可用」的前提下，暂不引入。

## 6. 使用与分发

按 C6（内部、不上网、单机），分发层就是**本机文件访问 + 元数据目录检索**，不引入任何网络服务。

| 环节 | 方案 |
|------|------|
| 唯一入口 | 元数据目录（§7 阶段 1）——所有数据先检索、后访问 |
| 访问方式 | Python API（`MarineDataPipeline` / `TimeAssembler` / `SourceAligner`）+ GUI（完成后的唯一图形入口） |
| 导出 | CSV / Excel / NetCDF（已实现），供内部协作与论文出图 |
| 权限控制 | 单人使用无需账号体系；若未来多人，用 Windows 文件权限 + 只读共享（列为未来可选，当前不上网） |
| 使用纪律 | 原始层只读；懒加载、不整库 `load()`/`.values` |

## 7. 缺口与路线

### 7.1 分期

| 阶段 | 内容 | 优先级 | 状态 |
|------|------|--------|------|
| 0 | 路径单点管理（`src/core/paths.py`） | 高 | ✅ 已完成 |
| 1 | 元数据目录升级：`config.yaml` → 结构化目录，补齐**时间/空间覆盖、溯源、文件大小、盘位置** | 最高 | 待做 |
| 2 | 冷存储分盘落地：按「来源×时间」分盘，目录记录盘位置，按需挂载读取 | 规模增长时 | 待做 |
| 3 | GUI 完成为唯一入口；导出链路收尾 | 中 | 待做 |

### 7.2 明确不做（对应约束 C2–C7）

校验（checksum）、质量控制（QC flag）、备份/RAID、网络分发（ERDDAP/THREDDS）、DOI/公开、新增数据来源。

### 7.3 待你确认的一个实现选择

阶段 1 的元数据目录用**什么载体**，两种都单机、无需服务器：

- **结构化 YAML**（沿用 `config.yaml` 扩展）——零依赖、可读、git 可追踪；适合条目几百以内。
- **SQLite 单文件**——查询/排序更强、增量更新方便、Windows 原生；适合条目上万。

> 建议：数据量到数百 TB、文件数可能上万时选 **SQLite**；若近期规模不大，先扩展 YAML 成本最低。这条不阻塞整体方向，可稍后定。

## 8. 风险与变更

### 8.1 风险提示（记录，不改变决策）

1. **无校验 + 无备份 = 数据不可恢复**。代价需知情：
   - **可从源再生**：CMEMS（可重新下载）、标准化产物（可从原始重算）——风险低。
   - **不可再生**：自采渔业调查数据、自跑 ROMS 输出——单副本下丢失即永久丢失。仅作提示，不违背 C4。
2. **NTFS 上限**：单卷 ~256 TB。跨越该阈值时需分卷（或多盘），或评估 ReFS。
3. **目录层是唯一索引**：目录一旦丢失，数百 TB 冷数据等于「找不到」——目录是轻量文本/单文件，天然易多拷一份（这不属于 C4 的数据备份范畴）。

### 8.2 变更流程

任何违背 C1–C7 的变更（新增来源、启用校验/QC/备份、上网络分发等），先修改 §0 决策记录并说明理由，再动工实现——保证「决策」与「实现」不脱节。
